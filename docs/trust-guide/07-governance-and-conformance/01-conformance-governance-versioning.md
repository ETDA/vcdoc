# 7.1 การตรวจสอบ/รับรอง, ธรรมาภิบาล และการจัดการเวอร์ชัน

ต่อจาก [บทที่ 6 ความปลอดภัยและความเป็นส่วนตัว](../06-security-and-privacy/01-verifier-confidence-and-registration.md) บทนี้ (บทที่ 7) อธิบายว่าใครเป็นผู้ควบคุมกฎของระบบ (Governance), ขั้นตอนรับรอง/เพิกถอน Entity, และนโยบายจัดการเวอร์ชันเมื่อมีการเปลี่ยนแปลง

## 7.1 การตรวจสอบและการรับรอง (Conformance & Certification)

ETDA ยังไม่ได้ออกมาตรฐานการตรวจสอบและการรับรองฉบับเต็ม ด้านล่างนี้เป็นสิ่งที่ทำ ณ ตอนนี้เท่านั้น

### 7.1.1 การรับรอง

- ETDA (Governance Authority) เป็นผู้ตรวจรับรอง อนุมัติ และเพิ่ม entity เข้า Trusted List
- ใบรับรองมีอายุตาม `valid_from` – `valid_until` ของแต่ละ service ต้องต่ออายุก่อนหมด
- ETDA suspend หรือ revoke ได้ทั้งระดับองค์กร (org `status`) และระดับบทบาท (service `status`)

## 7.2 ธรรมาภิบาล (Governance)

ETDA ยังไม่ได้ออกมาตรฐานธรรมาภิบาลฉบับเต็ม ด้านล่างนี้เป็นสิ่งที่ทำ ณ ตอนนี้เท่านั้น

ETDA เป็น Governance Authority และ Trust Service Provider ETDA วางกฎ อนุมัติผู้เข้าร่วม และดูแลบริการกลาง เช่น Trusted List และ API Key

### 7.2.1 การเข้าและออกจากระบบ

- **เข้า:** Entity ลงทะเบียนกับ ETDA → ETDA ตรวจและอนุมัติ → ได้ API key → ถูกเพิ่มเข้า Trusted List ด้วย `status: active` (ดู § 6.1.1, § 5.2.1)
- **ออก:** ETDA suspend หรือ revoke ได้ทั้งระดับองค์กร (org `status`) และระดับบทบาท (service `status`) (ดู § 5.2, § 5.2.1)
- เมื่อ `status` ไม่ใช่ `active` → consumer (Wallet / Verifier / Issuer) ปฏิเสธทันที และคนอื่นจะไม่เชื่อ credential ที่เกี่ยวข้องอีกต่อไป

**ผลย้อนหลังต่อ credential ที่ออกไปแล้วก่อนถูก revoke:**

การ revoke ระดับ Entity/Issuer (org หรือ service `status`) **ไม่เท่ากับ** การ revoke credential รายใบผ่าน Status List (ดู § 3.2.5 / § 6.2.3):

| กรณี | ผลต่อ VC ที่ออกไปแล้วก่อนหน้า (อยู่ใน Wallet ผู้ใช้) |
|------|-------------------------------------------------------|
| Issuer ถูก **suspend** (ชั่วคราว) | VC เดิมยัง verify ผ่านทาง cryptographic signature ได้ แต่ Verifier ที่ตรวจ Trustlist สดจะเห็นว่า Issuer ไม่ `active` ณ ขณะตรวจ — **SHOULD** ปฏิเสธจนกว่า Issuer จะกลับมา `active` |
| Issuer ถูก **revoke** (ถาวร) | เช่นเดียวกับ suspend แต่เป็นการถาวร — VC ที่ออกโดย Issuer นี้ **MUST** ถือว่าไม่น่าเชื่อถืออีกต่อไปสำหรับ verifier ที่ตรวจ Trustlist ตาม timestamp ปัจจุบัน |
| ผู้ใช้ต้องการเพิกถอน VC ใบใดใบหนึ่งโดยเฉพาะ (ไม่ใช่ทั้ง Issuer) | ใช้กลไก Status List ของ VC นั้นโดยตรง (ดู § 3.2.5) — ไม่กระทบ VC ใบอื่นของผู้ใช้คนเดียวกันหรือ Issuer เดียวกัน |

- Entity/Issuer **MUST** แจ้งผู้ถือ VC (ผ่านช่องทางของตนเอง) หากทราบว่าตนเองถูก suspend/revoke และ VC ที่เคยออกจะไม่ผ่านการตรวจสอบอีกต่อไป
- รายละเอียดกระบวนการอุทธรณ์เพื่อกลับเข้าสู่สถานะ `active` ดู § 7.2.2

### 7.2.2 กระบวนการอุทธรณ์และการกลับเข้าสู่ระบบ (Appeal Process)

> **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ — ขั้นตอนด้านล่างเป็นแนวทางชั่วคราว (interim) ETDA จะประกาศกระบวนการฉบับเต็มในเวอร์ชันถัดไป]**

เมื่อ Entity ถูก suspend หรือ revoke แนวทางการอุทธรณ์ชั่วคราวมีดังนี้:

| ขั้น | ผู้ดำเนินการ | รายละเอียด |
|------|-------------|-----------|
| 1 | Entity | ติดต่อ ETDA ผ่านช่องทางที่ระบุใน § 7.5.4 พร้อมระบุเหตุผลที่เชื่อว่าการ suspend/revoke ไม่ถูกต้อง หรือรายงานการแก้ไขปัญหาที่เป็นสาเหตุ |
| 2 | ETDA | พิจารณาคำอุทธรณ์และหลักฐานการแก้ไข |
| 3 | ETDA | แจ้งผลการพิจารณา — คืนสถานะ `active` หรือคงสถานะ suspend/revoke พร้อมเหตุผล |

- **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]** ระยะเวลาการพิจารณาคำอุทธรณ์ — ETDA จะประกาศ SLA ในเวอร์ชันถัดไป
- Entity ที่ถูก revoke ถาวรและต้องการสมัครใหม่ **SHOULD** ดำเนินการตามขั้นตอนสมัครปกติ (§ 7.5) พร้อมชี้แจงประวัติการถูก revoke ครั้งก่อน

## 7.3 การจัดการเวอร์ชันและการเปลี่ยนแปลง

ระบบมีเวอร์ชัน 2 ชุดที่ต้องดูแลแยกกัน: เวอร์ชันของ **เอกสาร framework นี้** และเวอร์ชันของ **Trusted List**.

### 7.3.1 นโยบายเวอร์ชัน

- **เอกสาร framework:** ใช้เลข `[X.Y]` ที่ header พร้อม Status `Draft` หรือ `Final` (ดูส่วนหัวเอกสาร)
- **Trusted List:** มี `id` แบบ versioned (เช่น `urn:etda:trusted-list:2026-v1`), `@context` ระบุ version ของ TL format, และ `issued` / `next_update` บอกรอบ publish (ดู § 5.2.1)
- **Protocol:** แต่ละ service ประกาศ version ที่รองรับใน `protocols` (เช่น `OID4VCI_1.0`, `OID4VP_1.0`)

### 7.3.2 Backward Compatibility

- `protocols` ให้แต่ละ entity บอกว่ารองรับ protocol version ไหน เพิ่ม version ใหม่ได้โดยไม่ทำให้ของเดิมพัง
- ETDA หมุน trust anchor key ได้โดยไม่ต้อง redeploy app
- `valid_from` / `valid_until` ให้ key เก่าและ key ใหม่ทำงานทับกันได้ในช่วงเปลี่ยนผ่าน

### 7.3.3 นโยบายแจ้งเตือน Breaking Change ล่วงหน้า

> **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ — แนวทางด้านล่างเป็นข้อเสนอชั่วคราว (interim) ETDA จะยืนยัน/ปรับปรุงในเวอร์ชันถัดไป]**

| ประเภทการเปลี่ยนแปลง | ตัวอย่าง | ระยะเวลาแจ้งล่วงหน้า (เสนอ) | ช่องทางแจ้ง |
|------------------------|----------|-------------------------------|---------------|
| Breaking change ต่อ schema ของ Trusted List | เปลี่ยนโครงสร้าง field บังคับใน TL entry | **อย่างน้อย 90 วัน** | Trusted List `next_update` + ช่องทางแจ้งข่าวของ ETDA (ดู § 7.5.4) |
| เปลี่ยน protocol version ที่บังคับ | ยกเลิกรองรับ `OID4VCI_1.0` เดิม | **อย่างน้อย 90 วัน** พร้อม deprecation period ที่ทั้ง version เก่า/ใหม่ทำงานคู่กัน | เช่นเดียวกับข้างต้น |
| Non-breaking change (เพิ่ม field/protocol version ใหม่แบบ backward-compatible) | เพิ่ม `OID4VCI_1.1` โดยยังรองรับ `1.0` | ไม่บังคับระยะเวลาแจ้งล่วงหน้า แต่ **SHOULD** ระบุใน Change Log (§ 7.3.4) | Change Log |

- Entity **SHOULD** ติดตามช่องทางแจ้งข่าวของ ETDA เป็นระยะเพื่อไม่พลาดประกาศ breaking change

### 7.3.4 Change Log

- Trusted List publish ตามรอบ — ดู `issued` และ `next_update` Entity ดึงฉบับใหม่เมื่อของเดิมหมดอายุ (freshness check ด้วย `exp`, ดู § 6.2.3)

## 7.4 Conformance Testing

> **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ — เนื้อหาด้านล่างเป็นแนวทางขั้นต่ำชั่วคราว (interim) ETDA จะประกาศ test suite ฉบับเต็มในเวอร์ชันถัดไป]**

### 7.4.1 Sandbox / Staging Environment

- **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]** Endpoint ของ Sandbox/Staging แยกจาก Production (`trust.etda.or.th`) — ETDA จะประกาศ URL ที่แน่นอนพร้อมขั้นตอนสมัครสิทธิ์เข้าใช้งานในเวอร์ชันถัดไป
- แนวคิดที่วางแผนไว้: Entity ใหม่ควรได้ทดลอง integrate กับ Sandbox ก่อนขึ้น Production เสมอ เพื่อลดความเสี่ยงจาก integration bug ในระบบจริง

### 7.4.2 Test Suite ขั้นต่ำที่ควรผ่าน (แนวทางชั่วคราว)

| # | Test Case | ผลลัพธ์ที่คาดหวัง |
|---|-----------|---------------------|
| 1 | ออก VC ตัวอย่าง (ผ่าน OID4VCI flow เต็ม) ใน Sandbox | ได้ VC ที่ signature valid และ schema ตรงตาม `credential_type` ที่ขออนุมัติ |
| 2 | Wallet/Verifier ดึง Trustlist ผ่าน Sandbox Trust Gateway | ได้ Trustlist ที่มี entry ของ Entity ตัวเองครบถ้วน |
| 3 | Verifier ตรวจ VP request/response ผ่าน OID4VP flow เต็ม | ผ่านทุกจุดตรวจใน Common Verification Pattern (ดู [1.4 หลักการตรวจสอบ — ใครตรวจใคร](../01-concepts-and-roles/03-common-verification-pattern.md)) |
| 4 | จำลอง entity ที่ `status` ไม่ใช่ `active` | consumer ปฏิเสธ credential ที่เกี่ยวข้องตามที่คาดไว้ (ดู § 7.2.1) |

- **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]** เกณฑ์ผ่าน/ไม่ผ่านที่เป็นทางการ และจำนวน test case เต็มรูปแบบ — ETDA จะประกาศเพิ่มเติม

## 7.5 ขั้นตอนสมัครเป็น Issuer

> **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการทั้งหมด — เนื้อหาด้านล่างรวบรวมจากขั้นตอนที่ทำอยู่ ณ ปัจจุบัน (ดู § 6.1.1) และเติมช่องว่างด้วยแนวทางชั่วคราว (interim) ที่มี placeholder ชัดเจนสำหรับส่วนที่ ETDA ยังไม่ประกาศ]**

ภาพรวมขั้นตอนสำหรับองค์กร (ทั้งภาครัฐและเอกชนที่ผ่านเกณฑ์ ETDA — ดู `01-concepts-and-roles/01-glossary.md`) ที่ต้องการสมัครเป็น **Issuer**:

### 7.5.1 เอกสารที่ต้องเตรียม

| เอกสาร/ข้อมูล | หมายเหตุ |
|-----------------|----------|
| ข้อมูลองค์กร (นิติบุคคล, ใบอนุญาตประกอบธุรกิจที่เกี่ยวข้อง) | **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ — รายการใบอนุญาตที่ ETDA ต้องการจะประกาศตามประเภทธุรกิจ]** |
| Public key / DID ที่จะใช้เซ็น VC | ดู § 6.1.1.1 กรณีใช้ Custom DID |
| รายชื่อ `credential_type` ที่ต้องการขออนุมัติออก | อ้างอิงตัวอย่างที่ `05-trust-infrastructure/02-tl-json-examples.md` |
| ระดับ LoA ของแต่ละ `credential_type` ที่จะออก | ใช้กำหนดข้อกำหนด HSM ที่ต้องปฏิบัติตาม (ดู § 6.2.2 ตาราง LoA ↔ HSM) |
| แผนการเก็บ signing key (softkey/HSM) ตามระดับ LoA | ดู § 6.2.2 |

### 7.5.2 เกณฑ์ที่ ETDA ใช้ตรวจสอบ (Audit)

- ตรวจความครบถ้วนของเอกสารตาม § 7.5.1
- ตรวจ security assessment เบื้องต้น (รายละเอียดเกณฑ์เต็ม **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]**)
- ตรวจผ่าน Conformance Testing ใน Sandbox ตาม § 7.4 ก่อนอนุมัติเข้า Production Trustlist

### 7.5.3 ระยะเวลาโดยรวม

| ขั้นตอน | ระยะเวลาโดยประมาณ |
|---------|----------------------|
| เตรียมเอกสาร (Entity) | ~1 วัน ถึงหลายสัปดาห์ ขึ้นกับความพร้อมขององค์กร |
| ETDA ตรวจและอนุมัติ (Audit) | **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]** |
| ทดสอบใน Sandbox (Conformance Testing) | **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]** |
| ออก API key + เพิ่มเข้า Production Trustlist | ทันทีหลังผ่านทุกขั้นตอนข้างต้น |

> ETDA จะประกาศ SLA ที่เป็นตัวเลขชัดเจนของแต่ละขั้นตอนในเวอร์ชันถัดไป ผู้สมัคร Issuer ควรวางแผน timeline ธุรกิจโดยเผื่อระยะเวลาที่ยังไม่ fix นี้ไว้

### 7.5.4 ช่องทางติดต่อ

> **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ — หากยังไม่มีช่องทางที่ระบุไว้ ณ ที่นี้ ให้ถือว่าอยู่ระหว่างการพิจารณาของ ETDA จะประกาศในเวอร์ชันถัดไป]**

- อีเมล/เว็บไซต์ลงทะเบียนอย่างเป็นทางการของ ETDA: **[รอ ETDA ประกาศ]**
- ช่องทางนี้ใช้สำหรับ: สอบถามการสมัคร, ยื่นคำขอ Custom DID (§ 6.1.1.1), ยื่นคำอุทธรณ์ (§ 7.2.2), ยื่นคำขอเพิ่ม `credential_type` (§ 7.5.5)

### 7.5.5 การขอเพิ่ม `credential_type` หลังผ่านการอนุมัติครั้งแรก

Issuer ที่ต้องการออก `credential_type` เพิ่มเติมจากที่ได้รับอนุมัติครั้งแรก **ไม่ต้องสมัครใหม่ทั้งหมด** — ดำเนินการยื่นคำขอแก้ไข (amendment) ดังนี้:

| ขั้น | ผู้ดำเนินการ | รายละเอียด |
|------|-------------|-----------|
| 1 | Entity | ยื่นคำขอเพิ่ม `credential_type` ผ่านช่องทางใน § 7.5.4 พร้อมระบุ LoA ของ credential type ใหม่ |
| 2 | ETDA | ตรวจสอบตามเกณฑ์ § 7.5.2 เฉพาะส่วนที่เกี่ยวกับ credential type ใหม่ (ไม่ต้องตรวจซ้ำทั้งองค์กร) |
| 3 | ETDA | อัปเดต `allowed_credential_types` ของ Entity ใน Trusted List |

- **[ยังไม่ได้กำหนดค่ามาตรฐานอย่างเป็นทางการ]** ระยะเวลาของกระบวนการ amendment — คาดว่าเร็วกว่าการสมัครใหม่เนื่องจากไม่ต้องตรวจข้อมูลองค์กรซ้ำ

| Response time เป้าหมายของ API | **[รอ ETDA ประกาศ]** |
| ค่าใช้จ่ายในการลงทะเบียน/เข้าร่วมระบบ | **[รอ ETDA ประกาศ — ยังไม่ยืนยันว่าฟรีหรือมีค่าใช้จ่าย]** |
| ตัวเลข Rate Limit / Quota ของ API Gateway | **[รอ ETDA ประกาศ]** — ระหว่างนี้ Entity ที่คาดว่าจะมี throughput สูง (เช่น ออกบัตรพร้อมกันหลักหมื่นใบ/วัน) **SHOULD** ติดต่อ ETDA ผ่าน § 7.5.4 เพื่อขอ quota เฉพาะ (dedicated tier) |

## 7.7 Audit Log ขั้นต่ำชั่วคราว (Interim Minimum)

ETDA ยังไม่ได้ออกมาตรฐาน Audit Log ฉบับเต็ม (ดู § 6.2.4) ระหว่างรอประกาศ Issuer/Entity **SHOULD** เก็บ audit log ขั้นต่ำดังนี้เพื่อลดความเสี่ยง rework เมื่อมาตรฐานเต็มออกมา:

| รายการ | คำแนะนำขั้นต่ำชั่วคราว |
|--------|---------------------------|
| เหตุการณ์ที่ควรบันทึก | การออก VC ทุกครั้ง (พร้อม credential ID), การตรวจ/ปฏิเสธ VP ทุกครั้ง, การดึง Trustlist ใหม่ทุกครั้ง, การเปลี่ยนแปลง signing key |
| ระยะเวลาเก็บ | อย่างน้อย 1 ปี (ปรับเพิ่มได้เมื่อ ETDA ประกาศมาตรฐานจริง) |
| รูปแบบ | JSON หรือ structured log ที่ query ย้อนหลังได้ (ยังไม่บังคับ schema ตายตัว) |

> คำแนะนำนี้เป็นแนวทางชั่วคราวเท่านั้น ไม่ใช่ข้อบังคับที่ ETDA ประกาศอย่างเป็นทางการ
